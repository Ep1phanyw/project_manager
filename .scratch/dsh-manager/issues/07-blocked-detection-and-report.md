# 07: 阻塞判定与报告

**What to build:** 只有三种情形能进入阻塞：同一部分连续两次验收失败且失败原因未变、缺少只有用户能提供的东西、需要改动验收标准本身。阻塞时产出一份报告，说明卡在哪、试过什么、需要用户提供什么；模型宣称阻塞一律无效。

**Blocked by:** 06

**Status:** in-review

- [x] 同一部分连续两次验收失败且原因未变时自动进入阻塞
- [x] 缺少只有用户能提供的东西时可进入阻塞，并说明缺什么
- [x] 需要改动验收标准时可进入阻塞，并说明为什么现有标准做不到
- [x] 除上述三种情形外，模型宣称阻塞被拒
- [x] 阻塞时产出报告：卡在哪、试过什么、需要用户提供什么
- [x] 模型无法自行降低验收标准，只能提出建议并等待用户裁决

## 验证记录

- **三种情形是唯一的入口**：阻塞只能由 `requestBlock` 产生，它对照 `BLOCK_CONDITIONS` 白名单，别的说法一律拒并列出允许值。
- **「连续两次同样失败」由插件自己数**，不由模型声称：`repeatFailureReason` 去记录里取同一部分最近两次 `returned`，理由不一样就不构成。模型或子对话声称这一条但记录对不上时被拒 —— 这是 ADR-0001 从提示词挪到返回值的具体落点。
- **自动阻塞**：验收不通过时插件自己检查，一旦构成连续同因失败就追加一条阻塞记录，不等谁宣布。两次理由不同则不阻塞。
- **阻塞报告**：`blockReport` 摊出「卡在哪个部分 / 是什么情形 / 需要你做什么」。子对话报的阻塞带上 `blockedCondition`，缺了会被判回报不合规。
- **降标准没有入口**：状态机没有任何修改验收标准的方法（有测试断言这四个名字都不存在）。模型只能提出「需要改验收标准」这个请求，改不改由用户决定。
- **测试**：13 条阻塞测试；115 条总计。

## 留给 08 / 09 的

- 阻塞后没有任何动作能让项目继续 —— 用户 `accept` 降标准 / 补上缺的东西之后如何恢复，票 08 才装。
- 「待用户确认」仍然是死胡同（08）。
- 所有部分验收通过后仍没有「项目完成」状态（09）。
