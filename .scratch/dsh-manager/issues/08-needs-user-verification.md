# 08: 待用户确认

**What to build:** 有些部分的证据只能由用户亲眼判断。子对话回报「待确认」时，项目停下、把材料摊给用户，`/manager confirm` 后才继续；在此之前该部分不算完成。

**Blocked by:** 06

**Status:** in-review

- [x] 子对话回报「待确认」时项目停下，不再派分下一部分
- [x] 停下时把该部分产出的材料呈现给用户
- [x] 该部分在用户确认前不算完成，也不会被重复派分
- [x] `/manager confirm` 后该部分转为完成，循环继续
- [x] 用户拒绝时该部分回到可重派状态并记录原因

## 验证记录

- **停下而不是重跑**：`nextPart` 见到「待确认」就停，不会把这一部分再派一遍。
- **材料摊开**：`/manager` 的状态文本多一段「待你确认」，列出部分编号、标题、摘要与每条证据的第一行。
- **确认才算完成**：新增记录状态 `confirmed`（用户已确认）。完成判定要求它是**用户**写的，并且前面紧挨着同轮次的「待确认」记录 —— 手写一条确认同样绕不过去。
- **确认与打回都要理由**，且只认 `by: 'user'`；模型侧调用直接拒。
- **打回即回到可重派**：记一条 `returned`（理由进摘要），`nextPart` 立刻又会挑中这一部分。
- **只有一份材料时不要求指定部分**：多个部分同时等确认时才要求点名。
- **测试**：11 条确认测试；130 条总计。

## 评审后的加固

- **用户打回不再记成「验收不通过」**：新增 `declined` 状态。之前打回写的是 `returned`，会被「连续两次同样失败」当成验收失败，用户打回一次 + 验收失败一次就能凑出阻塞 —— 那是 ADR-0001 不允许的。
- **确认的证据门槛与验收一致**：`confirmed` 也要求前置记录带证据，手写一条无证据的「待确认」+「确认」不再能凭空完成一个部分。
- **改计划不能跳过待确认**：有部分在等确认时 `submitPlan` 直接拒绝（和阻塞同等对待）。
- **确认不必写理由**：票面只要求打回写原因；确认没写说明就记一句默认的。
- **材料看全**：待确认段落把证据的每一行都摊出来，不只第一行。
- **轮次计数**改用 `isVerdictStatus`，四种裁决状态统一排除。

## 留给 09 的

- 阻塞之后仍然没有恢复动作：用户补上缺的东西、或同意改验收标准之后怎么继续，还没装。
- 所有部分完成之后仍然没有「项目完成」状态。
