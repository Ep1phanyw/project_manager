# 04: 只有用户能批准计划

**What to build:** 计划必须由用户批准。模型侧调用批准会被拒绝，`/manager approve` 才能通过；未批准前，取下一个可派分的部分只会得到「尚未批准」，不会返回任何部分。

**Blocked by:** 03

**Status:** in-review

- [x] 模型侧调用批准操作被拒，计划仍处于未批准
- [x] 用户通过 `/manager approve` 能批准计划
- [x] 未批准时取下一个可派分部分返回「尚未批准」，不返回部分
- [x] 批准动作在状态里留痕
- [x] 用户驳回后计划回到可编辑状态，可以重新提交

## 验证记录

- **两道锁**：结构上一把 —— 没有任何工具暴露批准，模型无从调用；核心里第二把 —— `approvePlan` / `rejectPlan` 只接受 `by: 'user'`。
- **闸门不信状态行**（评审后重做）：`阶段：` 写的是普通 markdown，有文件写权限就能改。所以 `nextPart` 要求**审批历史最后一条确实是「批准」**，手把 `阶段：awaiting-approval` 改成 `executing` 也派分不了。有专门的测试钉住这一点。
- **批准后计划仍可改**（评审后重做）：原实现是「必须先驳回才能改」，反了 spec 故事 24。现在直接改就行，但会追加一条「计划更新」记录并把项目退回**待批准**，必须重新批准才能继续派分 —— 改动有痕、要重新校验。
- **批准前重新校验计划**：`plan.md` 被手改坏或依赖不合法时，批准被拒，不允许批准一份读不懂的计划。
- **阶段流转**：`planning` →（提交）`awaiting-approval` →（批准）`executing`；驳回退回 `planning`，批准中途撤销也退回 `planning`。
- **留痕格式**：`project.md` 的 `## 审批` 段，一行一条 `- <ISO 时间> 批准|驳回|更新`，驳回带理由。理由不许换行（否则写坏记录）。
- **驳回必须写理由**：没有理由的记录等于没留下信息。
- **测试**：19 条状态机测试 + 2 条命令路由测试（`/manager approve`、`/manager reject` 走真实文件存储）。
- **待用户确认**：`/manager approve` 是斜杠命令，只能由用户在会话里敲。
