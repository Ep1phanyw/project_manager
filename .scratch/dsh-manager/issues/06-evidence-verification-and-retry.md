# 06: 证据验收与重派

**What to build:** 主对话拿子对话交回的证据对照验收标准核对，判定通过或不通过。通过才算该部分完成；不通过则记录失败原因并允许重派，重试次数递增。模型无法把这部分直接标记为完成。

**Blocked by:** 05

**Status:** in-review

- [x] 回报带符合要求的证据时判为通过
- [x] 缺证据或证据不可复现时判为不通过，并记录失败原因
- [x] 模型无法把这部分直接标记为完成
- [x] 判为不通过后该部分可被重新派分，重试次数递增
- [x] 每次失败的失败原因被保留，供后续判断「失败原因是否变化」

## 验证记录

- **`done` 不再等于完成**：子对话报 `done` 只写成「候选完成」。`nextPart` 见到候选完成就停下并要求先验收，不会往下派分，也不会把这一部分重跑。
- **验收是独立动作**：新增 `manager_verify` 工具，`pass` / `fail` 都要写理由 —— 没有理由的验收等于没人看过。
- **通过的硬条件**：必须存在候选完成记录、该记录必须带证据、必须写明理由；缺一条就拒绝。这是「模型无法直接标记完成」的落地：它不能跳过候选回报直接宣布，也不能不写理由。
- **不通过即回到可重派**：记一条 `rejected`（理由存进摘要），`nextPart` 立刻又会挑中这一部分，轮次递增。
- **失败原因保留**：`failed` / `invalid` / `rejected` 三类记录都留在 `parts.md`，可按部分取出来比较「这次和上次是不是同一个原因」—— 票 07 判阻塞要靠它。
- **轮次只数派分结果**：验收记录不计入轮次，否则验收一次就把轮次顶掉了（写这一票时踩到，已修并有测试）。
- **测试**：10 条验收测试；97 条总计。

## 评审后的加固

- **手写记录绕不过验收**：一条「验收通过」必须前面紧挨着同部分、同轮次、带证据的「候选完成」，否则显示为「验收记录不完整」、不算完成。手写一行 `- 状态：accepted` 骗不过去（有测试）。
- **验收要过阶段闸门**：计划退回待批准时不能验收。
- **改计划即作废旧结果**：重新提交计划会清空派分记录，免得旧的「验收通过」被算到新计划头上。
- **验收记录带上它所验收的证据**：之前通过记录把证据丢了，事后无从复核；现在原样保留。

## 留给 07 / 08 / 09 的

- `blocked` 三条件闸门仍在提示词里，没有落在返回值上（07）。
- 「连续两次同样原因失败」现在可以数出来，但还没有据此自动判阻塞（07）。
- 子对话报「待用户确认」的部分目前是死胡同：`verifyPart` 只收 pass/fail，`nextPart` 又拒绝派分，还没有让用户点头的动作（08）。
- 所有部分都验收通过后没有「项目完成」这个状态，`nextPart` 会误报「剩下的都被未完成的部分挡着」（09）。
- 「证据可复现」最终仍是主对话的判断，插件只能保证形状（有证据、类型对得上）与留痕（理由写进记录）。
