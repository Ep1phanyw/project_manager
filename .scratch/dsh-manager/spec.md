# dsh-manager — 项目编排插件

Status: ready-for-agent

## Problem Statement

我在一个会话里让 agent 做一整个项目时，会遇到三件互相纠缠的事：

1. **上下文债务**：细节在同一个窗口里越积越多，前期的规划被后面的实现噪音埋掉，越跑越糊。
2. **假完成**：模型会在某个时刻宣布「做完了」，而它停下时的样子和真正完成一模一样，我很难分辨。
3. **失焦**：一个会话同时承担「想清楚做什么」和「把每件事做完」，两件事抢同一个上下文。

我想要的不是更强的模型，而是一次交付能被**拆开**：每一块在干净上下文里做完，只把结果带回来；而「完成」这件事由我说了算。

## Solution

一个 DSH 插件 `dsh-manager`。我用一条 `/manager` 命令把**当前会话**指定为**主对话**。主对话先跟我确认**项目**目标，并逐条问出**验收标准**；然后产出一份**计划**，每个**部分**写清它的依赖、涉及的文件集和要求的证据类型，交我批准。批准后，主对话按顺序把每个部分分派给一个**子对话**：子对话在独立上下文里干活，只交回一份结构化结果；主对话拿**证据**对照验收标准核对，不过就重派。循环一直跑到「全部达标」或触发**阻塞**为止 —— 阻塞只发生在三种被我认可的情形下，且必须出报告由我裁决。

项目状态全部落在 `.scratch/` 下的普通 markdown 里，能 diff、能 review、能手改。

## User Stories

1. 作为项目发起人，我想用一条命令把当前会话指定为主对话，这样我不必为了「当指挥」另开一个会话。
2. 作为项目发起人，我想在项目开始时就一次性说清目标，这样后面的部分不会各自漂移。
3. 作为项目发起人，我想让主对话**逐条提问**帮我把验收标准问清楚，这样我不会漏掉自己其实很在意的条件。
4. 作为项目发起人，我想在批准计划前看到每个部分依赖谁、碰哪些文件，这样我能当场发现两个部分其实耦合。
5. 作为项目发起人，我只想由**我**批准计划，模型不能自己开跑。
6. 作为项目发起人，我想让每个部分跑在独立上下文里，这样长项目不会把主对话的窗口撑爆。
7. 作为项目发起人，我想子对话**只返回结果**，不要把它思考的全文塞回主对话。
8. 作为项目发起人，我想子对话的完整记录留在盘上，事后能查它到底干了什么、为什么这么做。
9. 作为项目发起人，我想每个部分都必须有**可复现的证据**才算完，不是模型说 OK 就 OK。
10. 作为项目发起人，我想验收不过时自动重派，而不是每一步都停下来问我。
11. 作为项目发起人，我想只在真正卡住时才被打断，而不是被常规进度打断。
12. 作为项目发起人，我想被打断时看到一份阻塞报告：卡在哪、试过什么、需要我提供什么。
13. 作为项目发起人，我不想让主对话自己降低验收标准 —— 要降必须提出建议并等我点头。
14. 作为项目发起人，我想随时问一句进度，知道哪些部分完成、哪些在跑、哪个卡住。
15. 作为项目发起人，我想关掉会话再打开还能接着跑，状态不丢。
16. 作为项目发起人，我想让某些部分停下来等我亲眼确认（例如界面外观），而不是被逼着编一个假证据。
17. 作为项目发起人，我想依赖关系显式写在计划里，这样以后打开并行开关时是安全的。
18. 作为项目发起人，我想第一版就是串行，不拿正确性换速度。
19. 作为项目发起人，我想插件只支持我当前的 DSH 版本；版本不匹配时明确告诉我，而不是装作能用。
20. 作为项目发起人，我想项目状态是普通 markdown，能进版本管理、能被我和别的 agent 直接读。
21. 作为项目发起人，我想在计划中途加一个部分时，插件重新校验依赖与证据类型，而不是默默接受。
22. 作为项目发起人，我想知道某个部分重试了几次、每次为什么没过。
23. 作为项目发起人，我想在子对话回报「待确认」时看到它产出的材料，而不是一句「请你看看」。
24. 作为项目发起人，我想计划被批准后仍然能改，但改动要留痕、要重新校验。
25. 作为项目发起人，我想明确知道项目此刻处于哪个阶段（规划 / 待批准 / 执行 / 待我确认 / 阻塞 / 完成），而不是靠猜。

## Implementation Decisions

**驱动模型**：模型开车。插件注册一条命令和一组工具；主对话是普通会话，插件**不**驱动它，也不替它生成提示。插件负责持有状态、计算下一步、并堵死作弊路径。护栏因此必须靠工具返回值强制执行 —— 不能靠提示词。

**ProjectState 核心**：一个不依赖 DSH 运行时的状态机 + 校验器，通过三项注入的能力接触外部世界：跑一个子对话、读写项目状态、向用户提问。上层工具只是薄适配器，把模型调用翻译成核心操作。

**核心操作**：启动项目、提交计划、批准计划、取下一个可派分的部分、记录子对话回报、验收一个部分、查看状态。

**计划校验**：每个部分必须声明依赖（可空）、涉及的文件集、证据类型。依赖必须指向计划内已存在的部分且不形成环。文件集重叠的部分之间必须有显式依赖，否则计划被拒 —— 这条把「互不影响」的判断从推断变成声明。

**证据类型**：`test`（测试通过）、`build`（构建成功）、`command`（某条命令的输出现场可复现）、`artifact`（生成的产物可检查）。证据必须可复现；「我确认过了」不构成证据。

**子对话回报**：结构化的，至少包含状态、摘要、证据清单、以及阻塞原因（仅当状态为阻塞时）。状态取值只有三种：完成、待用户确认、阻塞。

**验收判定**：由插件根据证据与验收标准给出通过 / 不通过 / 待用户确认，模型不能直接写「完成」。驳回时记录失败原因，用于判断「连续两次失败且原因未变」。

**阻塞判定**：由插件依据状态判断，不依赖模型自觉。三种情形之外一律不允许宣布阻塞。

**分派顺序**：取第一个「依赖已完成」且未完成的部分；v1 严格一次一个。

**状态持久化**：项目状态、验收标准、每部分的记录，全部落在 `.scratch/` 下（遵循本仓库既有的 issue tracker 约定），markdown，人可读可改。

**版本约束**：只支持当前 DSH 版本，用引擎约束写死；不满足时安装即失败。

**零运行时依赖**：不自带框架，测试用 Node 内置测试运行器。

## Testing Decisions

**什么算好测试**：只从 ProjectState 的公共接口驱动、只观察它的返回值和落盘状态；不测私有函数、不替内部结构造断言。一个测试应当像「一次用户故事」：启动项目 → 提交计划 → 批准 → 派分 → 回报 → 验收。

**被测对象**：ProjectState 核心的全部判定 —— 计划校验（含环检测与文件集重叠规则）、分派顺序、验收判定、阻塞判定、状态往返读写。

**替身**：跑子对话、读写状态、问用户、时钟，四项全部注入假件。子对话永远返回预制汇报，因此测试里没有模型、没有网络、没有真实文件系统竞争。

**不做**：不测 Cordis 装配、不测 DSH 自身行为、不测真实模型的输出质量。另加一个安装后的冒烟检查，确认命令与工具确实注册成功 —— 那是接线检查，不算行为接缝。

**先例**：本仓库全新，没有既有测试可对齐。这一版同时确立测试风格：接缝只有一个，替身全是注入的，测试按用户故事命名。

## Out of Scope

- 并行执行（依赖与文件集先建好，开关留到后续版本）
- git worktree 隔离
- 「真会话」形态的子对话
- 任何图形界面（进度看 `.scratch/` 里的 markdown）
- 同时管理多个项目
- 多版本 DSH 兼容矩阵
- 发布到插件市场
- 自动提交 git、自动开 PR

## Further Notes

- **入口命令是 `/manager`**（已定）；工具名沿用同一命名域，不另起一套词汇。
- 子对话一层、并发上限 8 是平台事实（子代理默认深度 1），v1 不试图突破它。
- 验收权归用户、主对话不得自我宣布达标，已记录为 ADR-0001；这条是本设计的核心安全属性，不是可调参数。
- 「模型开车」的代价：模型可以绕过软提示，所以每条护栏都必须落在工具返回值上 —— 这是实现时最容易走形的地方。
