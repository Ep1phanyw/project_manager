# 平台适配靠能力探测，不靠版本号闸门

## 背景

本插件有两道闸门，失效方式都是**静默**的：

1. `engines.dsh` 不满足时，启动期会把插件行改写成 `disabled: true`，只往 stderr 打一行，插件代码里不会走任何分支。
2. `inject` 声明四项平台能力，缺任一项时 fiber 停在 PENDING，`apply()` 一次都不执行，同样不打日志。

本机安装里没有 CHANGELOG，升级指南只覆盖到已安装版本，更上层的破坏性变化无据可查 —— 所以「读升级说明、提前适配」这条路走不通。静默消失这个失效方式，比报错更难查。

## 决定

把平台能力分**硬**、**软**两类。

- **硬**：命令注册、工具注册、工作目录。缺任一项插件没有存在意义，继续走 `inject` —— 缺了就不加载，这是正确的失败方式。
- **软**：子对话。不写进 `inject`，运行时探测；缺失时不假装能执行，而是明说本环境跑不了项目，并允许只做规划与查看。

`engines.dsh` 保留上限（挡住会导致大面积改版的将来版本），但不再作为「能力是否可用」的判据。版本号只用于提示「这个版本不在已验证清单里」。自检报告已安装版本、已验证清单，以及每项能力的实际存活情况。

## 考虑过的选项

- **继续写死版本、逐版本升区间**：升级 DSH 那天插件静默消失，用户看到的是「插件不见了」，而不是「缺什么」。否决。
- **完全去掉 `engines.dsh`**：任何版本都加载，包括能力面已改到面目全非的将来版本，会以「活着但半坏」的状态跑。否决。
- **维护多版本兼容矩阵**：没有升级文档可依，成本落在猜测上。否决。

## 后果

- 插件可能在未验证的 DSH 版本上「活着但少一条腿」。这是刻意取舍：可诊断的降级胜过静默消失。
- 服务缺失不能再用「方法存不存在」这类守卫探测，必须走运行时的服务查找；错误的探测方式会把「服务缺失」误判成「服务可用」。
- 测试多出一条接缝：能力缺失时插件应有的行为（降级、报告、拒绝派分）。
