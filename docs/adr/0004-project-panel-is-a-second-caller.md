# 项目面板是状态机的第二个调用者，不做第二个实现

## 背景

「在界面上看项目、点批准」本质上是同一套 `createProjectState` 状态机上的第二次调用。现在已有两条调用路径：`/manager` 的 14 个关键字（人）与 7 个 `manager_*` 工具（模型）。再加一条 UI 路径时，最省事的写法是把规则复制一份到前端——哪些按钮该亮、状态能不能跳、批准要不要校验计划合法性。一旦复制，验收纪律就有了两个实现，二者漂移时错误只出现在 UI 里。

## 决定

项目面板只做两件事：**摊开状态**、**在三处用户专属裁决上替用户提交决定**——批准计划、判断型部分确认、收尾验收确认。

- 所有校验、状态迁移、留痕仍由宿主侧 `createProjectState` 完成；面板不自己推导迁移规则，按钮的显示条件只读宿主返回的状态字段，点击失败就把宿主原文显示出来。
- 三处裁决的「打回」必须能填理由：`reject` 的理由在状态机里是必填的。
- 维护动作（改标准重批、重新钉契约、迁移格式、放弃项目、解除阻塞）首版不进 UI，留在命令里。

## 考虑过的选项

- **把 14 个关键字全做成按钮**：低频维护动作最容易被误点，且每个都得在 UI 里复算前置条件。否决。
- **面板自己算按钮可用性**：前端变成状态机的第二份实现，改一处要改两处。否决。
- **纯只读、一个按钮都不接**：批准门正是最痛的「离开聊天去翻上下文」处，纯只读等于把痛点原样留着。否决。

## 后果

- 面板取数据与提交动作都要经宿主半，因此多一条 Host→Client 通道：宿主注册只读 JSON 路由，页面 `fetch` 轮询。这条通道是本设计里最脆的一环，先交付只读面板正是为了先把它打穿；若验证不可行，退回 DSH 的 typert Remote，或改成会话级面板复用内置远程能力。
- 三处裁决在 UI 与命令各有一个入口，共享同一套校验；命令不删，任一边失败都给宿主原文。
- 以后要加维护动作，应加在 `createProjectState` 的方法上，而不是在 UI 里写新逻辑。
