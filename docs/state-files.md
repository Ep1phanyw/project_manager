# 状态文件

每个项目一个目录：`.scratch/<项目名>/`，里面五个普通 markdown 文件。写哪几个文件、以什么顺序落盘由 `lib/store.js` 决定；每一行的格式由 `lib/project-state.js`（前三个文件与 `project.md`）、`lib/records.js`（`parts.md` 与 `acceptance-run.md`）决定，读回时按同一套格式解析。

```
.scratch/<项目名>/
├── project.md        # 项目本身：名字、阶段、格式版本、目标、审批记录、验收指纹、编号登记
├── acceptance.md     # 逐条验收标准，每条带一个检查
├── plan.md           # 部分清单：依赖、证据类型、覆盖的验收标准、文件集
├── parts.md          # 每次派分与裁决的记录
├── acceptance-run.md # 收尾验收的记录
└── logs/             # 检查的完整输出（记录里只留尾巴，这里留全文）
```

下面每个文件先给一份渲染出来的样子，再逐行说明。

## project.md

```
# <项目名>

阶段：<planning | awaiting-approval | executing>
格式：2
验收指纹：<16 位十六进制>

## 目标

<目标正文>

## 验收

- AC-1 在
- AC-2 退役

## 契约

- test/login.test.js a1b2c3d4e5f60718

## 标准

- AC-1 16f60cb173e3683e 2026-11-23T05:00:00.000Z -
- AC-2 885a05f2f365d6f7 2026-11-23T06:10:00.000Z 2026-11-23T06:10:00.000Z

## 审批

- <ISO 8601 时间> 批准
- <ISO 8601 时间> 驳回：<理由>
- <ISO 8601 时间> 更新
```

| 行 | 说明 |
| --- | --- |
| `# <项目名>` | 一级标题。项目名是启动项目时给的名字；目录名是把它里面的空白换成 `-`。解析时必须有这一行。 |
| `阶段：<值>` | 三个值之一：`planning`（规划）、`awaiting-approval`（待批准）、`executing`（执行）。解析时必须有这一行。派分闸门不单独信任它，另外要求「审批」里最后一条确实是批准。 |
| `格式：<版本号>` | 状态文件的格式版本。没有这一行的是 v1 项目：只能看状态，派分与验收一律被拒，直到 `/manager migrate`。迁移会先备份到同一项目目录下的 `backup-v1/`，再把验收标准迁成新格式（一律判断型）、给旧计划自动分配覆盖；**原来批准过的保留批准**（审批历史里追加一条「迁移：覆盖已自动分配」），没批准过的退回待批准。 |
| `验收指纹：<16 位十六进制>` | 可选，第一次批准时才写入。内容是当时验收标准（含每条标准的检查）按编号排序后渲染全文的 sha256 前 16 位。批准之后再改 `acceptance.md`，指纹对不上，派分与验收会被拒绝，直到重新批准。按编号排序意味着重排文件不改指纹。 |
| `## 目标` | 必有。下面的正文可以多行，读回时去掉首尾空白。正文里不能有 markdown 标题行或以「阶段：」开头的行，启动项目时会被拒绝。 |
| `## 验收` | 可选。记录每个验收标准编号的下场：`在`（当前存在）或 `退役`（被删掉过）。退役的编号不再回到标准里 —— 编号是身份，覆盖关系绑在它上面。 |
| `## 契约` | 可选。验收依据文件与它的内容指纹（sha256 前 16 位）。批准时钉下来；之后谁改了这些文件，验收与派分都会停下，直到用户 `/manager contract` 重新钉指纹。没有指纹的一行是「还没批准」的状态。 |
| `## 标准` | 可选。每条标准的**检查**指纹、批准时间，以及它上一次「检查真的变过」的时间（没变过写 `-`）。没有这一节的项目按「全部已批准」读。改标准的文字会让整份指纹对不上（要重批计划）；只改检查时，只有这一条变成待批准，由 `/manager approve-criteria` 单独批准。 |
| `## 审批` | 可选。还没有任何审批记录时，这一节连同它前面的空行都不写。 |
| `- <时间> <批准｜驳回｜更新>` | 每条审批一行，时间是 ISO 8601（UTC，带毫秒）。驳回时后面接 `：<理由>`（驳回必须有理由）；批准与更新通常不带说明。认不出的一行不会让项目消失，但会让派分与批准都拒绝执行，直到这一行被修好。 |

空行是固定的分隔：标题与 `阶段：` 之间一个，`## 目标` 前后各一个，`## 审批` 前一个；文件以换行结尾。

## acceptance.md

```
# 验收标准

## [AC-1] <第一条>

- 检查：命令 node --test
- 期望退出码：0

## [AC-2] <第二条>

- 检查：判断型
```

| 行 | 说明 |
| --- | --- |
| `# 验收标准` | 标题行。解析时标题和空行都会被跳过。 |
| `## [AC-<编号>] <正文>` | 每条标准一个块，编号形如 `AC-1`。编号是标准的身份：它不会因为重排而改变，删掉的编号会被记进 `project.md` 的「## 验收」并从复用中排除。正文不能包含换行。 |
| `- 检查：命令 <命令>` | 命令检查：验收时由插件执行这条命令。同一块里还可以有 `- 期望退出码：<非负整数>`（省略为 0）、`- 输出匹配：<正则>`，以及 `- 允许空输出：是`（这条命令本来就不输出东西时必须写）。既没有输出匹配、也没有允许空输出，项目启动就会被拒。 |
| `- 检查：产物 <路径>` | 产物检查：验收时检查这个文件。可以再跟一行 `- 内容匹配：<正则>`。 |
| `- 检查：判断型` | 无法机械核对的标准，只能由用户亲眼判断。它没有别的检查字段，也不会被执行任何命令。 |

每条标准必须有且只有一个检查；既没有检查、也没标判断型的标准会让项目启动被拒绝。判断型标准里不能出现别的检查字段。一条都没有的验收标准同样会被拒绝，项目也就读不出来。

## plan.md

```
# 计划

## [P1] <标题>

- 依赖：无
- 证据：artifact
- 覆盖：AC-1
- 文件：docs/state-files.md

## [P2] <标题>

- 依赖：P1
- 证据：artifact
- 覆盖：AC-2
- 文件：README.md
```

| 行 | 说明 |
| --- | --- |
| `# 计划` | 标题行。渲染时总会有；解析时和空行一起被跳过。 |
| `## [P<编号>] <标题>` | 每个部分一个；编号形如 `P1`。标题不能包含换行。计划里至少要有一个部分。 |
| `- 依赖：<P 编号>` | 每个依赖一行；没有依赖时写 `- 依赖：无`。依赖必须指向计划里存在的部分，且不能成环。 |
| `- 证据：<类型>` | 每个部分恰好一行，类型只能是 `test`、`build`、`command`、`artifact` 之一。 |
| `- 覆盖：<AC 编号>` | 这条标准归这个部分管，一个编号一行；没有归属时写 `- 覆盖：无`。覆盖了不存在的编号会被拒；每条验收标准都必须至少被一个部分覆盖，否则计划本身是缺陷。一条标准可以同时归多个部分。 |
| `- 文件：<路径>` | 每个文件一行，合法计划里至少有一行。路径写回时统一成 `/` 分隔，去掉开头的 `./` 和结尾的 `/`。 |

部分与部分之间空一行。两个部分改同一片文件（路径相同，或一个目录包含另一个）却没有先后依赖时，计划提交会被拒绝。

## parts.md

没有记录时文件只有一行：

```
# 部分记录
```

每次派分的结果、每次验收结论、每次用户裁决都追加一条记录，一条记录长这样：

```
## [P1] 第 1 次 · <ISO 8601 时间>

- 状态：done
- 子会话：<子会话 id>

### 摘要

  <摘要正文，可多行，每行缩进两个空格>

### 证据

  - <证据 1>
  - <证据 2 的第一行>
    <证据 2 的续行>

### 检查

  - AC-1 通过：命令 node --test → 退出码 0（期望 0）
    输出：ok
  - AC-2 不通过：命令 node --test → 退出码 1（期望 0）
    输出：断言失败

### 阻塞原因

  <阻塞说明>
```

| 行 | 说明 |
| --- | --- |
| `## [P<编号>] 第 <次数> 次 · <时间>` | 一条记录一个标题。次数从 1 开始，按这一部分已记录的非裁决结果递增；验收、确认、打回、解除阻塞这些裁决记录沿用最近一次派分的次数。 |
| `- 状态：<状态值>` | 必有，取值见下表。 |
| `- 子会话：<id>` | 可选，回报带了会话 id 时才写。 |
| `- 实例：<id>` | 可选，只在在飞记录上写：说明这条在飞是哪个进程起的。实例与本进程不同，这条就是上一次进程断在半路留下的「中断」。 |
| `- 越界：<文件>` | 可选，子对话动了声明之外的文件时写。并列写着「（并行期间不可靠）」时，表示那次派分是并行的，归属仅供参考。 |
| `- 情形：<情形值>` | 可选，只在主对话通过 `manager_block` 请求阻塞时写，取值 `repeated-failure`、`missing-user-input`、`criteria-change`。子对话回报的阻塞、以及插件自动判定的「连续两次同样原因验收失败」，都不写这一行。 |
| `### 摘要` | 可选，有摘要才写。裁决记录（`accepted`、`returned`、`confirmed`、`declined`、`resolved`）改用 `### 理由` 作标题。标题下一行留空，正文缩进两个空格。 |
| `### 证据` | 可选，有证据才写。每条以 `  - `（两个空格加短横）起头，续行缩进四个空格。 |
| `### 检查` | 可选，只有插件跑过检查的记录才有（验收结论、以及因检查而生的待确认）。每条一行 `- AC-n 通过/不通过：<说明>`，说明的第二行起是要复核的原始输出，缩进四个空格。 |
| `### 阻塞原因` | 可选，只有阻塞记录才有。正文缩进两个空格。 |

状态值：

| 状态值 | 含义 | 由谁写 |
| --- | --- | --- |
| `running` | 在飞 | 派分时插件写；回报落盘时清除。实例不是本进程的就是「中断」 |
| `done` | 候选完成 | 子对话回报完成 |
| `needs-user-verification` | 待确认 | 子对话认为需要用户亲眼看；或插件跑完检查、这部分还覆盖着判断型标准（收尾验收也用它） |
| `blocked` | 阻塞 | 子对话回报阻塞；或连续两次同样原因验收失败时插件自动记一条 |
| `failed` | 子对话出错 | 子对话执行失败或抛异常 |
| `invalid` | 回报不合规 | 回报缺摘要、缺证据、证据类型不对等 |
| `accepted` | 验收通过 | 插件跑完检查，全过且不涉及判断型标准 |
| `returned` | 验收不通过 | 插件跑完检查，有标准没过 |
| `confirmed` | 用户已确认 | `/manager confirm` |
| `declined` | 用户打回 | `/manager decline` |
| `resolved` | 用户已处理阻塞 | `/manager resolve` |

子对话给的正文（摘要、证据、阻塞原因）一律缩进写入；只有顶格的行才会被当成结构行，所以子对话写不出新的结构行，也写不坏别的部分的记录。解析时遇到认不出的顶格行会报错，状态里显示「部分记录读不出来」。

## 读写的共同规则

- 写入顺序是 `parts.md` → `plan.md` → `acceptance.md` → `project.md`，`project.md` 最后落盘；它是「项目存在」的标记，所以写到一半失败不会留下一个能被列出却读不全的项目。
- `project.md` 的结构行必须顶格；`parts.md` 的正文必须缩进。手写时保持这两条，否则解析器会拒绝整份文件。
- `plan.md` 与 `parts.md` 对顶格行最严格：只接受上面列出的结构行，别的顶格行会让文件读不出来；`acceptance.md` 的非空非标题行也必须是 `## [AC-n]` 标题或上面列出的检查字段。
- 手改 `阶段：` 骗不过派分闸门：派分看的是「审批」里最后一条确实是批准。
- 重新提交计划会把 `parts.md` 清空重写（只留标题），免得旧计划的「验收通过」被当成新计划的完成。
- 四个文件都是普通 markdown，可以直接打开读。`parts.md` 读不懂时项目仍然可用，状态里会显示「部分记录读不出来」；`project.md` 缺标题、阶段或目标，或 `acceptance.md` 读不出条目时，整个项目会报可读的错误。
