# project_manager

把一次交付拆成若干**部分**，交给上下文独立的**子对话**；**主对话**负责规划、派分、验收。插件只出工具，开车的是主对话。

状态全部落在会话工作区的 `.scratch/<项目名>/` 下，是普通 markdown：跑完能读，卡住能查。

## 它是什么

- **主对话**是当前会话里负责指挥的那一个：启动项目、提交计划、派分部分、验收结果。
- **部分**是一次派分的工作单元：每次交给一个上下文独立的子对话，失败可重试。子对话只拿到这一部分的任务、文件范围和要求的证据类型（外加项目目标与验收标准），不继承主对话的上下文。
- **验收标准**在项目启动时定下，逐条可核对；每个部分的完成都要拿可复现的证据来换。
- **用户**保留三类裁决权：批准/驳回计划、确认/打回「待确认」的部分、解除阻塞。模型侧没有对应的工具。

术语的完整定义见 [GLOSSARY.md](GLOSSARY.md)，「验收归用户」的取舍见 [ADR-0001](docs/adr/0001-acceptance-belongs-to-the-user.md)。

## 安装

要求：

- DSH **0.2.3-alpha.2 以上、0.4.0 以下**（见 `package.json` 的 `engines.dsh`）。0.3.x 也能加载：插件按**运行时能力探测**工作，不按版本号猜接口；已验证版本清单在自检里。
- Node.js **>= 22**
- 本包没有运行时依赖，也没有构建脚本，不需要先跑构建

安装方式（二选一）：

1. **Plugins 页**：打开 DSH 的 **Plugins → Add plugin**，选择本仓库根目录（即 `package.json` 所在目录）。
2. **让主对话装**：主对话调用 `plugin_manager` 的 `install_bundle`，`target` 传本目录的绝对路径。

装好后：

- 在 Plugins 页确认 `project_manager` 一行已启用；
- 新开一个会话，输入 `/manager`。还没有项目时应该回「还没有项目；先在主对话里启动一个项目」。

本包通过 `cordis.patch.yml` 挂进配置树。**硬依赖三项能力**：`commands`、`tools`、`workingDirectory` —— 缺任一项插件就不加载，这是正确的失败方式。**子对话是软依赖**：缺了插件照常加载，规划、看状态都能用，但派分跑不了，`/manager doctor` 会明说「本环境跑不了项目」。

## 斜杠命令

`/manager` 在**没有项目**时是建项目的入口：它会输出一条三行的流程，并把三个上游技能注册成可被模型调用的别名（`project_manager-grill` / `project_manager-spec` / `project_manager-tickets`），正文走技能通道加载，对话里只留一个短标记。有项目时它照旧显示状态。

### 随包分发的三个技能

`/manager` 在没有项目时会用到三个技能，它们的正文**随本插件一起分发**（在包的 `skills/` 目录），装上就有，不需要另装：

| 原名 | 插件里的别名 | 用来做什么 |
| --- | --- | --- |
| `grill-with-docs` | `project_manager-grill` | 把需求问清楚，边问边把术语与决定落进 `GLOSSARY.md` 与 ADR |
| `to-spec` | `project_manager-spec` | 把访谈收敛成 spec，写到 `.scratch/<项目名>/spec.md` |
| `to-tickets` | `project_manager-tickets` | 把 spec 拆成带先后关系的部分，写成 `.scratch/<项目名>/issues/NN-*.md` |

**为什么注册两份**：技能目录里同名是「先注册者赢」。你本机若已装过同名技能（尤其它们标着 `disable-model-invocation: true`），插件用原名注册的那份就永远抢不到，模型也就调不到。带前缀的别名不会撞车，所以在任何机器上都可用。`/manager` 的流程指令指的是**别名**，就是因为这个。

两者的正文来源一致：**本地优先**（`~/.agents/skills/`，你改过就生效），本地没有才用包里那份。

本机也有同名技能时，只是多出三行 `project_manager-*` 条目，不会报错。

三个最常用的：

| 命令 | 作用 |
| --- | --- |
| `/manager` | 看当前项目状态：阶段、目标、逐条验收标准、审批记录、每个部分的状态与重试次数。`/manager status` 等价。 |
| `/manager approve` | 批准已提交的计划。批准后阶段从「待批准」变成「执行」，才允许派分部分。 |
| `/manager confirm [说明]` | 对「待确认」的部分点头。有些证据只能由你亲眼看（比如界面效果）；说明可省略，省略时会记一句默认说明。 |

全部命令：

| 命令 | 作用 |
| --- | --- |
| `/manager` 或 `/manager status` | 有项目时看状态；**还没有项目时**给出「grill-with-docs → to-spec → to-tickets → 提交计划」这条建项目流程，并尝试把它排进本会话。 |
| `/manager <项目名>` | 同时有多个项目时，指定要看哪一个。项目名里的空白会变成目录名里的 `-`。 |
| `/manager approve` | 批准计划，只认用户。计划没到「待批准」、或已经不合法时会被拒。 |
| `/manager reject [理由]` | 驳回计划，回到规划阶段。理由必填。 |
| `/manager confirm [说明]` | 确认当前唯一一个待确认的部分。没有待确认的部分、或有多个待确认时会报错。 |
| `/manager accept [说明]` | 确认收尾验收 —— 这一下才算项目完成。 |
| `/manager abandon <理由>` | 放弃项目。文件留着当存档，之后除了看状态别的操作全停。 |
| `/manager criteria` | 你手改完 `acceptance.md` 后跑它：重新读入、更新指纹、退回待批准。 |
| `/manager migrate` | 迁移旧格式项目：先备份到 `backup-v1/`，把旧标准迁成判断型，给旧计划自动分配覆盖。**原来批准过的，批准保留**（覆盖自动分配会写进审批历史）；没批准过的仍然要先批准。 |
| `/manager contract` | 契约文件被你有意改过之后跑它：重新钉指纹，退回待批准，重新批准之后才能继续。 |
| `/manager approve-criteria [AC-n …]` | 只改了一条标准的**检查**（不影响文字）时跑它：单独批准这一条，项目不退出执行阶段。按旧检查验过的部分会被标成「需重验」，可以重新派分。 |
| `/manager doctor` | 自检：DSH 版本、期望范围、每项依赖的能力在不在、git 可用性、技能注册情况。**升级 DSH 之后先跑它。** |
| `/manager decline [理由]` | 把待确认的部分打回重做；如果没有待确认的部分，则打回收尾验收。理由必填。 |
| `/manager resolve [说明]` | 你处理完阻塞后，让这个部分重新可派分。说明必填。 |

有多个项目时，除了看状态，其余命令都用 `@` 指定项目：`/manager reject @demo 太粗了`。

状态里出现「待你确认」时，会连同子对话的摘要与证据一起列出来，供你判断。

## 一次典型的项目

这些是主对话调用的工具，不是斜杠命令；你只需要在关键节点用上面的命令点头或打回。

| 工具 | 做什么 |
| --- | --- |
| `manager_start` | 启动项目：写下目标与逐条验收标准，**每条标准都要带一个检查**（命令、产物，或标成判断型）；可选地列出**契约文件**（测试、脚本这些验收依据）。状态落在 `.scratch/<项目名>/`。 |
| `manager_plan` | 提交计划：每个部分声明依赖、会改的文件、要求的证据类型，以及**覆盖哪几条验收标准**。依赖成环、两个部分改同一批文件却没有先后关系、有标准没被任何部分覆盖，都会被拒。 |
| `manager_run` | 派分可以开工的部分：互不依赖、文件集不相交的会**同时在独立上下文的子对话里跑**（上限取配置与平台剩余名额的较小者），其余一次一个。 |
| `manager_verify` | 验收一个部分：插件**亲自执行**这部分覆盖的每条检查，按结果给结论 —— 有检查没过就打回并附上明细，全过但有判断型标准就进「待你确认」，否则通过。模型给不了结论。 |
| `manager_accept` | 收尾验收：所有部分过完之后，先跑整体检查（若配置过）、再把全部标准的检查重跑一遍，把结果记下来等你点头。 |
| `manager_block` | 请求阻塞，或查看当前阻塞报告。不给 `condition` 时返回报告。 |

完整循环：

1. 你告诉主对话要做什么、怎样算做完；主对话调用 `manager_start` 定下目标与验收标准，**每条标准都带一个检查**（命令 + 期望退出码，或产物断言；机械核不了的标成判断型）。
2. 主对话用 `manager_plan` 提交计划，每个部分声明覆盖哪几条标准；有标准没人覆盖会被拒。阶段变成「待批准」。
3. 你用 `/manager` 看一眼，`/manager approve` 批准 —— 批准计划就等于批准了每条标准的检查。
4. 主对话用 `manager_run` 派分；互不依赖、文件集不相交的部分会同时跑。子对话完成后交回 `status / summary / evidence`。
5. **插件**执行这部分覆盖的检查并给出结论；通过后才轮到依赖它的部分。没过就打回，并把未通过的明细带回下一次派分。
6. 若某个部分还覆盖着判断型标准，状态显示「待你确认」，你 `/manager confirm` 或 `/manager decline [理由]`。
7. 所有部分都验收通过后进入收尾验收：主对话调 `manager_accept`，插件重跑全部检查，再由你 `/manager accept` 点头 —— 这一步之后才算完成。

## 状态文件

每个项目一个目录，都在**当前会话工作区**的 `.scratch/` 下：

```
.scratch/<项目名>/
├── project.md        # 目标、阶段、格式版本、审批记录、验收标准指纹、编号登记
├── acceptance.md     # 逐条验收标准（AC-1、AC-2 …），每条带一个检查
├── plan.md           # 部分清单：依赖、文件集、证据类型、覆盖的验收标准
├── parts.md          # 每次派分/验收/确认的历史，含检查的原始输出
└── acceptance-run.md # 收尾验收的记录
```

这些文件是插件的状态来源，可以直接读。手改要小心：

- 批准时会记下验收标准的指纹（含每条的检查定义）；批准之后再改 `acceptance.md`，插件会发现，并拒绝继续派分或验收，直到重新批准。
- 手改 `project.md` 里的「阶段：」一行骗不过派分闸门 —— 派分看的是审批历史里最后一条确实是「批准」。
- 子对话写的摘要与证据会缩进落盘，伪造不出新的结构行，也写不坏别的部分的记录。
- 没有 `格式：2` 这一行的是旧格式项目：只能看状态，要动先 `/manager migrate`。

## 边界

- 只有用户能批准或驳回计划、确认或打回待确认的部分、解除阻塞、迁移旧格式项目。模型侧没有这些入口。
- 阻塞只认三种情形：缺少只有用户能提供的东西、需要改动验收标准本身、同一部分**连续两次未通过的检查集合相同**（最后一种由插件自己数，模型声称不算）。其他情况不许宣布阻塞，也不许自行降低验收标准。
- **派分可以并行，验收不行**：互不依赖、文件集不相交的部分会同时在独立上下文里跑（默认最多 3 个、硬顶 8，且不超过平台剩余名额）；验收始终一次一个。
- 同一个部分不会同时在飞两次。进程断在半路留下的在飞记录会标成「中断」，要你 `/manager resolve` 才重派 —— 插件不替你重试。
- **命令检查不能「只比退出码」。** 每条命令检查要么给一条输出断言，要么显式声明「允许空输出」。验收时如果输出自己写着零个用例通过（`# pass 0`、`0 passing` 这类），退出码再漂亮也判不通过。检查的完整输出会另存到 `.scratch/<项目名>/logs/`，记录里留指针。
- **批准时会先跑一遍检查。** 如果某条检查在开工前就已经通过，`/manager approve` 会点名提醒——它可能在验一件已经做完的事，或者在空转。
- **工作区不安静就不验收。** 还有部分在跑（或断在半路）时，验收会被拒绝：那时跑出来的检查结果说明不了什么。
- **改标准分两种改法。** 改**文字**（「要什么」）会让整份验收标准指纹对不上，必须重新提交 / 重新批准计划；只改**检查**（「怎么验」）时，只有这一条变成待批准，`/manager approve-criteria` 单独批它即可，项目不退出执行阶段。按旧检查验收过的部分会被标成「需重验」。
- **验收依据不许改。** 你在启动项目时可以指定**契约文件**（测试、脚本、样例数据）。批准计划时插件记下它们的内容指纹；之后任何部分都不许把契约文件写进自己的文件集，谁改了这些文件，派分与验收都会停下，直到你 `/manager contract` 重新钉指纹并重新批准。
- 验收结论**由插件执行检查算出**：命令检查比退出码与可选输出正则，产物检查比文件与内容。子对话的「完成」只是候选；模型也没有覆盖它的入口。
- 判断型标准（界面外观、措辞）不参与机械验收，永远回到你面前。
- **状态跟着会话工作区走。** 项目在哪个目录的 `.scratch/` 下，就要在那个工作区的会话里驱动它 —— 在别的工作区敲 `/manager` 会告诉你找不到项目。这不是限制你，是保证状态不会被两个会话同时改。
- **整体检查只在 `manager_start` 时设定**，之后没有正式入口。忘了配的话，手改 `project.md` 加这一段，插件下次读就认：

  ```markdown
  ## 核对

  命令：node --test
  ```

  没配整体检查时，`/manager doctor` 会提示「收尾少一层」：收尾验收只能靠逐条标准的检查各自的结果。

## 大项目要用的三件事

**改计划不会把历史清掉。** `manager_plan` 再次提交时，**定义没变的部分保留它们已有的验收记录**（定义指标题、文件集、依赖、证据类型、来源、覆盖的标准；文件或依赖的顺序不算变化）。加一个部分不必把前面几十个重新验一遍；只有真被改过的部分才重来。把某个阻塞的部分从新计划里删掉也是允许的 —— 留在计划里才拦。

**「完成」要真的跑一遍检查。** 所有部分验收通过后，阶段变成**待收尾验收**，`allDone` 仍然是 `false`。这是主对话要调 `manager_accept`：插件先跑整体检查（若配置过），再把**全部标准的检查**重跑一遍；任何一条没过就整次不算数、不留记录。全过之后由你 `/manager accept` 点头。所以不会出现「每个部分都过、整体从没一起跑过」。

**每个部分验收通过后打一个 git 快照。** 默认只提交**这个部分声明的文件**（`git add -- <文件集>`），不碰工作区里别的东西。要提交整个工作区得显式配置 `snapshot: all`，不想提交就 `snapshot: off`。快照失败（不是仓库、没有改动、钩子报错）只是没有快照，不影响验收。验收是串行的，所以快照也是。

**越界改动会被记下来。** 子对话回报之后，插件用 `git diff HEAD` 看这一轮到底动了哪些文件；不在这个部分声明的文件集里的，记为「越界改动」，出现在派分结果、状态文本和记录里。并行派分时同一工作区里的改动互相交织，归属不可靠，这一点会标注出来（「并行期间不可靠」），只作提示、不当闸门。查不了（不是 git 仓库）就留空，不影响流程。覆盖已跟踪文件的改动与删除；新加的文件不算，那通常是这一部分自己的产出。

## 在已有代码的仓库里用

插件不要求从零开始。两种情况它区别对待：

- **空仓库**：`/manager` 直接进访谈流程。
- **已经有东西**：`/manager` 会先让你**读懂现状** —— 读 `README`、`GLOSSARY.md`、`docs/adr/`、入口文件与构建配置，产出一段「现状摘要」（做了什么、用了哪些约定、哪里不能动），再以它为基础上问「还差什么」。

派分时，子对话拿到的任务描述里也会列出工作区里实际存在的约定文件（`README.md`、`GLOSSARY.md`、`docs/adr/` 等），让它先读、再动手 —— 否则一个空上下文的子对话在半成品仓库里只会另起一套。

**它不做的**：不判断哪些部分「已经完成」。已有的活不要列进计划即可，插件只跟踪它自己派分出去的部分。
