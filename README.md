# dsh-project-manager-plugin

**把一次交付拆成若干部分、交给独立上下文的子对话并行完成，验收由插件自己跑检查；人只在三处点头。**

[上手](#上手) · [项目面板](#项目面板) · [斜杠命令](#斜杠命令) · [一次项目怎么转起来](#一次项目怎么转起来) · [状态文件](#状态文件) · [边界](#边界) · [更多文档](#更多文档)

## 它解决什么问题？

平时让模型做一件稍大的事，大多是「人守着终端」：它说做完了，你没法确认是不是真做完了；一个长项目从头到尾串着跑，改文档和改模块明明互不相干也要排队；一旦关掉窗口，事情就断了。

这个插件把「交付」当成一次有据可查的项目：

- **验收不是模型说了算。** 每条验收标准绑定一个检查（命令 + 期望退出码，或产物断言），由插件亲自执行、亲自算结论。子对话报「完成」只是候选。
- **能并行的就并行。** 互不依赖、文件集不相交的部分同时在独立上下文里跑；验收仍逐个进行。
- **只有人能过的关，模型过不去。** 批准计划、确认判断型部分、收尾点头，这三处只认用户，模型侧没有入口。
- **状态是普通 markdown。** 全部落在会话工作区的 `.scratch/<项目名>/` 下：跑完能读，卡住能查。

```text
你 ──目标与验收标准──▶ 主对话 ──计划──▶ 批准（你）
                          │
                          ├─▶ 子对话 P1 ─┐
                          ├─▶ 子对话 P2 ─┼─▶ 插件跑检查 ─▶ 打回 / 待你确认 / 通过
                          └─▶ 子对话 P3 ─┘
                                    全部通过 ─▶ 收尾验收 ─▶ 你点头 ─▶ 完成
```

## 上手

要求：

- DSH **0.2.3-alpha.2 以上、0.4.0 以下**（`engines.dsh`）。0.3.x 也能加载：插件按**运行时能力探测**工作，不按版本号猜接口。
- Node.js **>= 22**。
- 没有运行时依赖，也没有构建脚本，不需要先跑构建。

装法二选一：

1. **Plugins 页**：DSH 的 **Plugins → Add plugin**，选本仓库根目录（`package.json` 所在处）。
2. **让主对话装**：调 `plugin_manager` 的 `install_bundle`，`target` 传本目录的绝对路径。

装好后：

- Plugins 页确认 `dsh-project-manager-plugin` 一行已启用；
- 新开会话敲 `/manager`。还没有项目时它不会报错，而是给你一条建项目的流程；
- 想要图形界面，刷新页面后点侧栏的「项目面板」。

本包通过 `cordis.patch.yml` 挂进配置树。**硬依赖三项能力**：`commands`、`tools`、`workingDirectory` —— 缺任一项插件不加载，这是正确的失败方式。**子对话是软依赖**：缺了照常加载，规划与看状态都能用，派分跑不了，`/manager doctor` 会明说。

## 项目面板

侧栏一个条目，点开占中央栏，一屏摊开一个项目的状态，并把三处只有人能过的裁决放到按钮上。

- **入口**：侧栏「项目面板」（图标在「自动化任务」之后）；顶部可切换工作区，默认取最近有活动的那个。
- **能做什么**：看项目列表与详情（阶段、目标、验收标准及其检查与覆盖、部分状态与重试次数、审批历史、收尾验收）；批准计划、确认判断型部分、确认收尾验收，以及三处对应的「打回」（打回必须写理由）；有待批时侧栏图标上有一个小圆点。
- **不能做什么**：另外 11 个维护动作（`approve-criteria`、`contract`、`migrate`、`abandon`、`resolve`、`criteria` 等）仍只在 `/manager` 里；面板不派分、不验收、不判断状态迁移。
- **数据从哪来**：宿主半在本机 GUI 服务器上注册只读路由 `/manager-panel/projects`、`/manager-panel/project`，裁决走 `POST /manager-panel/gate`（只认同源请求）；每 2 秒轮询、窗口聚焦即刷、可手动刷新；刷新失败时保留上一次内容并标注可能已过期。
- **安装**：客户端半随包分发（`package.json` 的 `exports["./client"]` 与 `dsh.client`），装好 bundle 后刷新页面即可，不需要额外配置。

定位与取舍见 [ADR-0004](docs/adr/0004-project-panel-is-a-second-caller.md)，术语见 [GLOSSARY.md](GLOSSARY.md) 的「Project panel」「Final acceptance」。

## 斜杠命令

`/manager` 在**没有项目**时是建项目的入口：输出一条三行流程，并把三个上游技能注册成可被模型调用的别名，正文走技能通道加载，对话里只留一个短标记。有项目时照旧显示状态。

三个最常用的：

| 命令 | 作用 |
| --- | --- |
| `/manager` | 看当前项目状态：阶段、目标、逐条验收标准、审批记录、每个部分的状态与重试次数。`/manager status` 等价。 |
| `/manager approve` | 批准已提交的计划。批准后阶段从「待批准」变成「执行」，才允许派分。 |
| `/manager confirm [说明]` | 对「待确认」的部分点头。说明可省略，省略时记一句默认说明。 |

全部命令：

| 命令 | 作用 |
| --- | --- |
| `/manager <项目名>` | 同时有多个项目时指定看哪一个。项目名里的空白会变成目录名里的 `-`。 |
| `/manager reject [理由]` | 驳回计划，回到规划阶段。理由必填。 |
| `/manager accept [说明]` | 确认收尾验收 —— 这一下才算项目完成。 |
| `/manager decline [理由]` | 打回待确认的部分；没有待确认的部分时打回收尾验收。理由必填。 |
| `/manager resolve [说明]` | 你处理完阻塞后，让这个部分重新可派分。说明必填。 |
| `/manager abandon <理由>` | 放弃项目。文件留着当存档，之后除看状态外全部停手。 |
| `/manager criteria` | 手改完 `acceptance.md` 后跑它：重新读入、更新指纹、退回待批准。 |
| `/manager contract` | 契约文件被有意改过后跑它：重新钉指纹，退回待批准，重新批准后才能继续。 |
| `/manager approve-criteria [AC-n …]` | 只改了某条标准的**检查**时跑它：单独批准这一条，项目不退出执行阶段。 |
| `/manager migrate` | 迁移旧格式项目：先备份到 `backup-v1/`，旧标准迁成判断型，自动分配覆盖；原来批准过的，批准保留。 |
| `/manager doctor` | 自检：DSH 版本、期望范围、每项依赖能力、git、技能注册。**升级 DSH 之后先跑它。** |

有多个项目时，除看状态外其余命令用 `@` 指定：`/manager reject @demo 太粗了`。状态里出现「待你确认」时，会连同摘要与证据一起列出来。

### 随包分发的三个技能

`/manager` 在还没有项目时会用到三个技能，正文随本插件一起分发（包里的 `skills/`），装上就有：

| 原名 | 插件里的别名 | 用来做什么 |
| --- | --- | --- |
| `grill-with-docs` | `project_manager-grill` | 把需求问清楚，边问边把术语与决定落进 `GLOSSARY.md` 与 ADR |
| `to-spec` | `project_manager-spec` | 把访谈收敛成 spec，写到 `.scratch/<项目名>/spec.md` |
| `to-tickets` | `project_manager-tickets` | 把 spec 拆成带先后关系的部分，写成 `.scratch/<项目名>/issues/NN-*.md` |

**为什么注册两份**：技能目录里同名是「先注册者赢」。你本机若已装过同名技能（尤其它们标着 `disable-model-invocation: true`），插件用原名注册的那份就永远抢不到。带前缀的别名不会撞车，所以在任何机器上都可用；`/manager` 的流程指令指的就是别名。两者的正文来源一致：**本地优先**（`~/.agents/skills/`），本地没有才用包里那份。

这三个技能的作者是 **Matt Pocock**（<https://github.com/mattpocock/skills>，MIT，`Copyright (c) 2026 Matt Pocock`）。正文**逐字未改**地随包分发，完整声明见 [`THIRD-PARTY-NOTICES.md`](THIRD-PARTY-NOTICES.md)；本插件自己的许可见 [`LICENSE`](LICENSE)。

## 一次项目怎么转起来

下面这些是主对话调用的工具，不是斜杠命令；你只需要在关键节点点头或打回。

| 工具 | 做什么 |
| --- | --- |
| `manager_start` | 启动项目：目标 + 逐条验收标准，**每条标准都要带一个检查**（命令、产物，或标成判断型）；可选列出**契约文件**（测试、脚本这些验收依据）。 |
| `manager_plan` | 提交计划：每个部分声明依赖、会改的文件、证据类型，以及**覆盖哪几条标准**。依赖成环、文件重叠却没有先后、有标准没人覆盖，都会被拒。 |
| `manager_run` | 派分可开工的部分：互不依赖、文件集不相交的**同时**在独立上下文里跑（上限取配置与平台名额的较小者），其余一次一个。 |
| `manager_verify` | 验收一个部分：插件**亲自执行**这部分覆盖的每条检查，按结果给结论。模型给不了结论。 |
| `manager_accept` | 收尾验收：先跑整体检查（若配置过），再把全部检查重跑一遍，把结果记下来等你点头。 |
| `manager_block` | 请求阻塞，或查看当前阻塞报告。 |
| `manager_flow_skill` | 取流程技能的正文：本地优先，本地没有就用包里那份。 |

完整循环：

1. 你说要做什么、怎样算做完；主对话用 `manager_start` 定下目标与验收标准，每条都带检查。
2. 主对话用 `manager_plan` 提交计划，每个部分声明覆盖哪几条标准。阶段变成「待批准」。
3. 你看一眼，`/manager approve`（或在面板上点「同意，开始执行」）—— 批准计划就等于批准了每条标准的检查。
4. 主对话用 `manager_run` 派分；子对话完成后交回 `status / summary / evidence`。
5. **插件**执行检查并给结论；通过后才轮到依赖它的部分，没过就打回，并把未通过明细带回下一次派分。
6. 若这部分还覆盖判断型标准，状态显示「待你确认」，你 `/manager confirm` 或 `/manager decline [理由]`。
7. 全部通过后进入收尾验收：主对话调 `manager_accept`，插件重跑全部检查，再由你 `/manager accept` 点头 —— 这一步之后才算完成。

## 状态文件

每个项目一个目录，都在**当前会话工作区**的 `.scratch/` 下：

```text
.scratch/<项目名>/
├── project.md        # 目标、阶段、格式版本、审批记录、验收标准指纹、编号登记
├── acceptance.md     # 逐条验收标准（AC-1、AC-2 …），每条带一个检查
├── plan.md           # 部分清单：依赖、文件集、证据类型、覆盖的验收标准
├── parts.md          # 每次派分/验收/确认的历史，含检查的原始输出
└── acceptance-run.md # 收尾验收的记录
```

这些文件是插件的状态来源，可以直接读。手改要小心：

- 批准时会记下验收标准（含每条的检查定义）的指纹；批准后再改 `acceptance.md`，插件会发现并拒绝继续派分或验收，直到重新批准。
- 手改 `project.md` 里的「阶段：」一行骗不过派分闸门 —— 派分看的是审批历史里最后一条确实是「批准」。
- 子对话写的摘要与证据会缩进落盘，伪造不出新的结构行，也写不坏别的部分。
- 没有 `格式：2` 这一行的是旧格式项目：只能看状态，要动先 `/manager migrate`。

## 边界

- 只有用户能批准/驳回计划、确认或打回待确认的部分、解除阻塞、迁移旧格式项目。模型侧没有这些入口。
- 阻塞只认三种情形：缺少只有用户能提供的东西、需要改动验收标准本身、同一部分**连续两次未通过的检查集合相同**（最后一种由插件自己数）。其他情况不许宣布阻塞，也不许自行降低验收标准。
- **派分可以并行，验收不行**：默认最多 3 个、硬顶 8，且不超过平台剩余名额；验收始终一次一个。
- 同一个部分不会同时在飞两次。进程断在半路留下的在飞记录会标成「中断」，要你 `/manager resolve` 才重派 —— 插件不替你重试。
- **命令检查不能「只比退出码」**：要么给输出断言，要么显式声明「允许空输出」；输出自己写着零个用例通过（`# pass 0`、`0 passing` 这类），退出码再漂亮也判不通过。完整输出另存到 `.scratch/<项目名>/logs/`。
- **批准时会先跑一遍检查**：若某条在开工前就已经通过，`/manager approve` 会点名提醒 —— 它可能在验一件已经做完的事。
- **工作区不安静就不验收**：还有部分在跑（或断在半路）时拒绝验收，那时的结果说明不了什么。
- **改标准分两种**：改文字会让整份指纹对不上，必须重新批准计划；只改检查时只有这一条变成待批准，`/manager approve-criteria` 单独批它即可。按旧检查验收过的部分会被标成「需重验」。
- **验收依据不许改**：契约文件的内容指纹在批准时钉下；任何部分都不许把契约文件写进自己的文件集，谁改了，派分与验收都会停下，直到你 `/manager contract` 重新钉指纹并重新批准。
- 判断型标准（界面外观、措辞）不参与机械验收，永远回到你面前。
- **状态跟着会话工作区走**：项目在哪个目录的 `.scratch/` 下，就要在那个工作区的会话里驱动它，这也保证状态不会被两个会话同时改。
- **整体检查只在 `manager_start` 时设定**，之后没有正式入口。忘了配的话，手改 `project.md` 加上这一段，插件下次读就认：

  ```markdown
  ## 核对

  命令：node --test
  ```

  没配整体检查时，`/manager doctor` 会提示「收尾少一层」。

## 大项目要用的四件事

**改计划不会把历史清掉。** `manager_plan` 再次提交时，定义没变的部分保留已有验收记录（定义指标题、文件集、依赖、证据类型、来源、覆盖的标准；文件或依赖的顺序不算变化）。加一个部分不必把前面几十个重新验一遍；把某个阻塞的部分从新计划里删掉也是允许的。

**「完成」要真的跑一遍检查。** 所有部分验收通过后阶段变成**待收尾验收**，`allDone` 仍是 `false`；由主对话调 `manager_accept`，插件先跑整体检查、再重跑全部标准的检查，任何一条没过就整次不算数、不留记录。所以不会出现「每部分都过、整体从没一起跑过」。

**每个部分验收通过后打一个 git 快照。** 默认只提交**这个部分声明的文件**（`git add -- <文件集>`）；`snapshot: all` 提交整个工作区，`snapshot: off` 不提交。快照失败只是没有快照，不影响验收。

**越界改动会被记下来。** 子对话回报后，插件用 `git diff HEAD` 看这一轮到底动了哪些文件，不在声明文件集里的记为「越界改动」，出现在派分结果、状态文本与记录里。并行时归属不可靠，会标注「并行期间不可靠」，只作提示、不当闸门。

## 在已有代码的仓库里用

插件不要求从零开始：

- **空仓库**：`/manager` 直接进访谈流程。
- **已经有东西**：先让你**读懂现状** —— 读 `README`、`GLOSSARY.md`、`docs/adr/`、入口文件与构建配置，产出一段「现状摘要」，再以它为基础上问「还差什么」。

派分时，子对话的任务描述里也会列出工作区里实际存在的约定文件，让它先读、再动手 —— 否则空上下文的子对话在半成品仓库里只会另起一套。

**它不做的**：不判断哪些部分「已经完成」。已有的活不要列进计划即可，插件只跟踪它自己派分出去的部分。
